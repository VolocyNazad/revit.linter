# Добавление встроенной проверки

Порядок выполнения — строго по шагам. Каждый шаг закрывается перед следующим.

## Шаг 1. Договориться

Зафиксировать письменно, одним предложением с примером:

1. Критерий находки — что именно считаем плохим, а не «что-то не так».
2. Термины из официального интерфейса — как называется у пользователя, так пишется в сообщениях.
3. Где работает — проекты, семейства или везде.
4. К каким элементам применяется — категории, классы или типы целей.
5. Как показывать находку — если у целей нет геометрии, только выделение; если есть, ещё и показ. Любая комбинация с пунктами 3–4 — штатный случай.
6. Будут ли исправления и какие — фикс влияет на меню в отчёте, шаги обучения и объём тестов.

## Шаг 2. Написать тесты

Тесты — до кода проверки:

1. Минимум два кейса: находка есть и находки нет.
2. Тестовые модели строить только кодом, без внешних файлов. Шаблоны семейств выбирать по содержимому (модельное семейство), а не первый попавшийся файл.
3. Всё меняющее модель — строго внутри транзакций, включая создание менеджеров и импорт.
4. Запросы созданных типов — после коммита, с понятной ошибкой о том, что реально нашлось.
5. Что нельзя построить детерминированно (нужны бинарные файлы или в API нет пути) — не тестировать вслепую, а записать причину в `TODO.md`.

## Шаг 3. Изучить API

1. Каждый новый метод проверить по всем поддерживаемым версиям: есть ли вообще, с какой версии, бросает ли геттер, есть ли сеттер.
2. Искать короткими кусками имени плюс смысловым поиском.
3. Отсутствие API считать доказанным только после нескольких вариантов поиска.

## Шаг 4. Написать проверку

1. Проверка, оба фильтра и карточка в каталоге. Регистрация подхватывается сама, провайдер не трогаем.
2. Описания и сообщения сразу на двух языках, плюс строки в таблицы документации.
3. Все чтения из API, которые могут бросить исключение в зависимости от формы элемента, обернуть в защитные пробы: нечитаемое состояние — это «чисто», а не падение всего прогона.

## Шаг 5. Собрать под все версии

1. Проверить сборку под каждую поддерживаемую версию, а не только под свежую.
2. Ноль предупреждений — релиз их считает ошибками.

## Шаг 6. Проверить живьём

1. Сначала логи: какая сборка стоит, какая проверка активна, что в отчёте.
2. Если не сошлось — временное подробное логирование решения прямо в проверку: что код видит, что сравнивает, на чём решает. После починки обязательно убрать.
3. Теории проверять чтением цепочки вызовов, а не перебором правок.
4. Игнорирование доступно любой проверке автоматически: отдельная реализация не нужна. Проверьте, что находка исчезает после «Игнорировать» и возвращается после снятия записи в панели «Игнорирования».

## Шаг 7. Финиш

1. Убрать временное.
2. Собрать всё, прогнать тесты без Revit, живые тесты, тесты локализации и валидатор репозитория.
3. Журнал изменений не трогать — он собирается при релизе.
